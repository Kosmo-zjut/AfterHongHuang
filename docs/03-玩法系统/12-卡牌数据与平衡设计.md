# 12-卡牌数据与平衡设计

> 版本: 1.1.0 | 状态: B1 平衡包已冻结，待开发迁入 CardDefinition 并回归 | 最后更新: 2026-07-20
>
> 范围：巫祝当前全套卡牌的平衡审视、`CardDefinition Schema v1`、B1 数值包、调参与内部编辑器边界。本文件不修改代码，也不授权 UI/Core 用名称、职业或固定数值分支。

## 1. 事实来源与本轮结论

### 1.1 事实来源优先级

1. 当前运行时卡牌事实：`洪荒之后-code/scripts/Data/DataDefs.cs` 的 `CardInfo`、初始/奖励/Boss 池。
2. 玩法语义：`01-卡牌系统.md`、`02-战斗系统.md`。
3. 本文件：数据契约、平衡基线和建议目标。

当前代码侧共有 21 个唯一卡牌定义：4 张初始卡、4 张升级卡、10 张常规奖赏卡、3 张 ACT1 Boss 奖励卡。初始牌组的重复副本不等于新的定义。当前 `CardInfo` 只能表达主值、一次自损、一次副效果、单一目标模式和布尔消弭，不能作为长期编辑器的唯一模型。

### 1.2 本轮推荐默认方案

- 先迁移到 `CardDefinition Schema v1` 与校验器，再做 Godot 编辑器插件；不做玩家运行时编辑器。
- 运行时只结算结构化 `Effects`，显示只读本地化/预览字段；禁止解析卡名或描述文本。
- B1 已冻结为新的 `CardDefinition` 目标数据，见 §3.1；本轮不等待遥测，但只采用当前执行器已支持的单变量数值或消弭改动。`DataDefs.cs` 仍是迁移前的旧运行时快照，不得与 B1 目标混用。
- 消弭必须由显式效果表达。当前事实：`祝融残焰` 消弭；三张 Boss 卡均不消弭。旧文档中两张 Boss 卡标为消弭已在本轮修正。

### 1.3 设计边界

- `斗劲`、护体、易损、永炎、自损结算均在 `BattleState`；永久套牌只保存卡牌 ID，不能保存某次战斗的临时层数。
- `CardDefinition` 可预留诅咒、状态、友方、多目标和 X 费用，但 ACT1 生产池只启用现有可执行子集：斗击/术法、灵力费用、自身/单敌目标、伤害/护体/失去生命/施加斗劲/易损/永炎/消弭。
- 稀有度和奖励池是内容元数据；候选生成、冻结、领取、跳过、关闭与节点离场由奖励计划状态机处理。替换卡牌数据不得改变这些提交边界。

## 2. 卡牌价值模型与调参流程

### 2.1 五维审视法

不要用“面板伤害/费用”单一排序。每次改卡必须写出以下五维的预期变化：

| 维度 | 判断问题 | ACT1 记录项 |
|---|---|---|
| 每点灵力即时攻防/资源 | 本回合在目标敌人意图下，实际减少多少敌方生命或玩家损伤？ | 实伤、实际吸收、生命支付、未花灵力。 |
| 抽牌与灵力经济 | 是否压缩行动、释放灵力或增加有效手牌？ | 0 费使用率、卡手率、同回合可多打出的牌数。 |
| 构筑成型后的缩放 | 在后续回合/同类牌/道痕出现后，收益增长多少？ | 斗劲、易损、永炎的已兑现收益，不只记录施加层数。 |
| 风险与条件 | 自损、目标限制、消弭、时序和低血量是否构成真实代价？ | 因生命支付进入危险区、未能打出、未能兑现、过量护体。 |
| 遭遇需求覆盖 | 它解决哪类压力，是否只在一种局面通用最强？ | 弱怪、强怪、Boss 分组下的回合数与受伤。 |

即时护体只在本回合确有预期伤害时计入防御价值；易损与斗劲的价值按后续能实际打出的有效斗击折算；永炎按预期存活回合折算。这样避免把“未来可能很强”的牌当作已兑现即时收益，也避免因短战没来得及成长就误判所有缩放牌无价值。

### 2.2 数据只作证据的调参循环

1. 写问题：例如“零费斗劲是否让巫祝在 ACT1 强怪战过早稳定滚雪球？”
2. 选对照：按 Act、层区、敌人类型、当前生命、套牌规模、是否持有九乌坠日/体修金刚分组，不能把不同阶段混成一个均值。
3. 同时看指标与回放：候选出现数、选取率、入胜卡组率、战斗受伤、平均回合、单遭遇表现、未打出率及玩家反馈。
4. 提出一个最小改动假设，限定到单个数值、费用、消弭或目标条件，不同时改多个旋钮。
5. 用固定种子和相同起始状态回归，再用一轮新数据复核；若体感和数据相反，先检查分组、样本与结算日志。

完成 B1 验收并累计至少 50 次有效 ACT1 运行、且覆盖每个敌人类型后，才允许提出 B2。样本不足时只能登记观察，不自动 nerf/buff。选取率或入胜卡组率高低都不是因果结论，可能来自奖励出现时机、玩家生命、路径或其他卡的共同影响。

### 2.3 遥测最小字段

`runSeed`、Act/层、遭遇 ID、敌人类型、奖励候选 ID 与顺序、选择/跳过、进入战斗时生命和套牌、每张卡的抽到/打出/未打出、目标、实际伤害/护体/生命支付/状态兑现、胜负、回合数、战后生命。所有卡牌字段记录稳定 ID 与定义版本，不记录显示名称作为聚合键。

### 3.1 B1 可实施保守平衡包（冻结）

**适用定义版本：`balanceVersion = B1-20260720`。** 下表是开发部应写入 `CardDefinition` 的目标值；旧 `DataDefs.cs` 数值仅用于迁移前/后差异测试。B1 不改变稳定 ID、费用、稀有度、奖励池、目标策略、升级关系或状态种类，也不改变任何 Boss 卡的消弭状态。

| 稳定 ID | 旧定义 | B1 新定义 | 效果顺序 / 消弭 | 冻结理由 |
|---|---|---|---|---|
| `wx_02_p` | 1 灵力；获得 8 护体。 | 1 灵力；获得 **7** 护体。 | `GainBlock(Self, 7)`；不消弭。 | 与 `骨甲` 拉开 1 点，升级仍比基础格挡多 2。 |
| `wx_r_005` | 1 灵力；失去 2 生命，获得 12 护体。 | 1 灵力；失去 2 生命，获得 **10** 护体。 | `LoseHealth(Self, 2, CanCauseDefeat=true)` -> `GainBlock(Self, 10)`；不消弭。 | 降低“生命成本常被高护体覆盖”的净防御优势。 |
| `wx_r_006` | 0 灵力；失去 3 生命，获得 1 斗劲。 | 数值不变；**消弭**。 | `LoseHealth(Self, 3, CanCauseDefeat=true)` -> `AddStatus(Self, Strength, 1, Battle)` -> `MoveSelfToZone(Exhaust)`。 | 保留零费启动感，限制同一张牌在单场战斗的重复滚雪球。 |
| `wx_r_007` | 2 灵力；失去 2 生命，造成 11 伤害，施加 2 易损。 | 2 灵力；失去 2 生命，造成 11 伤害，施加 **1** 易损。 | `LoseHealth(Self, 2, CanCauseDefeat=true)` -> `DealDamage(SelectedTarget, 11)` -> `AddStatus(SelectedTarget, Vulnerable, 1, Battle)`；不消弭。 | 只下调后续放大，不同时压低即时伤害。 |
| `wx_r_008` | 1 灵力；失去 4 生命，获得 2 斗劲。 | 数值不变；**消弭**。 | `LoseHealth(Self, 4, CanCauseDefeat=true)` -> `AddStatus(Self, Strength, 2, Battle)` -> `MoveSelfToZone(Exhaust)`。 | 保留高风险成长，限制单卡循环叠斗劲。 |
| `wx_r_009` | 2 灵力；失去 3 生命，获得 18 护体。 | 2 灵力；失去 3 生命，获得 **16** 护体。 | `LoseHealth(Self, 3, CanCauseDefeat=true)` -> `GainBlock(Self, 16)`；不消弭。 | 保留强怪回合的专门防守，但降低过量护体。 |
| `wx_a1_boss_002` | 2 灵力；获得 20 护体，并获得 1 斗劲。 | 2 灵力；获得 **16** 护体，并获得 1 斗劲。 | `GainBlock(Self, 16)` -> `AddStatus(Self, Strength, 1, Battle)`；不消弭。 | 保留 Boss 奖励的守转攻定位，减少无条件最优倾向。 |

“生命支付可致败”沿用当前自损语义，必须在打出合法性与结算日志中显式体现；不得因卡牌名称或卡面文案决定该行为。上述 `Strength` / `Vulnerable` 是 Schema 内部效果枚举映射，游戏内显示仍使用斗劲 / 易损。

### 3.2 B1 明确维持的基线

下列卡牌在 B1 **维持迁移前基线**，开发部不得顺带调整：

| 范围 | 稳定 ID | 冻结口径 |
|---|---|---|
| 初始与升级 | `wx_01`、`wx_01_p`、`wx_02`、`wx_03`、`wx_03_p`、`wx_04`、`wx_04_p` | `拳袭+` 保持 1 灵力 9 伤害；`格挡`保持 5；其余效果、顺序、升级关系不变。 |
| 常规奖赏 | `wx_r_001`、`wx_r_002`、`wx_r_003`、`wx_r_004`、`wx_r_010` | `燎掌`保持 1 灵力 8 伤害，`骨甲`保持 1 灵力 8 护体；其余数值、目标和消弭状态不变。 |
| Boss 奖赏 | `wx_a1_boss_001`、`wx_a1_boss_003` | 数值、效果顺序和“不消弭”均不变。 |

拳袭+与燎掌的处理结论：B1 **不改** `wx_01_p: 9` 和 `wx_r_001: 8`。精进道行不增加套牌张数，战后拿燎掌会增加一张牌；这 1 点差异保留两种选择的不同价值，不需要为表面对齐而同时改两张纯伤害牌。

### 3.3 B1 验收与 B2 门禁

开发迁入 B1 时，必须执行以下验收；任何失败均不得以“数值主观可接受”跳过。

| 验收项 | 操作与通过条件 |
|---|---|
| 固定种子回归 | 使用同一 `RunSeed` 及其独立 `Encounter/Reward/Combat` 随机流、相同角色/初始生命/初始牌组和相同遭遇定义，分别跑迁移前基线与 B1。除 B1 目标字段及其直接结算结果外，地图、候选、敌人意图和无关随机结果保持一致。 |
| 定义字段回归 | 21 张卡逐张校验 ID、费用、类别、稀有度、奖励池、目标策略、升级关系；仅 §3.1 的 7 张允许差异，且差异逐字段等于 B1 表。 |
| 能量与生命支付 | 对每张改动卡在足额/不足灵力、足额/临界生命下尝试打出；费用不变，自损按表中顺序发生，`CanCauseDefeat=true` 的结果不得静默阻止或改写。 |
| 消弭 | `wx_r_006`、`wx_r_008` 结算一次后移入消弭区，本战斗不可再次抽到/打出；下一场战斗从永久套牌正常可用。其他 B1 卡不得因迁移被错误消弭。 |
| 短线覆盖 | 在固定弱怪遭遇与同一初始条件下，验证 7/10/16 护体文本和实际护体、11 伤害 + 1 易损、两张消弭斗劲卡的即时结算。 |
| 强怪 / Boss 覆盖 | 在固定强怪和 ACT1 Boss 遭遇中，以相同起始条件验证 `烬骨守势` 16、`九首回潮` 16 + 1 斗劲、消弭后不重复滚雪球，以及不会跨战斗保留斗劲。 |
| 结构与反硬编码 | 用两张同类别但名称、数值、目标/效果顺序不同的测试定义走相同奖励、预览与执行入口；UI/Core/Controller 不得按卡名、职业名、ID 或固定数值分支。 |

**B2 门禁：** B1 的上述回归全部通过后，累计至少 50 次有效 ACT1 运行，且弱怪、强怪、Boss 三类遭遇均有覆盖，才可基于选取率、入胜卡组率、受伤/回合损耗、遭遇表现和定性反馈提出下一轮改动。B1 期间只修实现错误，不再扩大或混入新的平衡改动。

## 4. CardDefinition Schema v1

### 4.1 顶层结构

| 字段 | 类型/示例 | 规则 |
|---|---|---|
| `schemaVersion` | `1` | 迁移和 Validator 的兼容边界。 |
| `id` | `wx_r_006` | 稳定、全局唯一；永久套牌、奖励计划和遥测只存此 ID。 |
| `display` | `nameKey`、`descriptionKey`、`effectSummaryKey`、开发 fallback | 本地化/显示专用；不得参与逻辑。 |
| `owner` | `ownerKind: Character/Neutral`，`characterId` 可空 | 中立卡不填角色；角色卡必须填集中角色 ID。 |
| `category` | `Attack` / `Skill` / `Power` / `Curse` / `Status` | 显示可映射为斗击/术法/道行/劫数；枚举不依赖文本。 |
| `costs` | `CardCostDefinition[]` | 费用列表，不再把生命支付藏在自损字段。 |
| `targetPolicy` | 见 §4.2 | 是交互和合法目标的唯一来源。 |
| `effects` | `CardEffectDefinition[]` | 有顺序、可校验；是结算唯一来源。 |
| `rarity` | `黄品/玄品/地品/天品` | 内容稀有度，不直接等同于随机算法。 |
| `rewardPoolIds` | `reward_cards` 等 | 多个池可引用同一张定义。 |
| `upgrade` | `canUpgrade`、`nextCardId`、`familyId` | 明确升级图，不能由名称加 `+` 推导。 |
| `tags` | `self_harm`、`strength`、`act1` | 搜索、筛选、平衡分组；不直接改效果。 |
| `availability` | `minContentVersion`、特性条件、禁用原因 | 控制版本/条件，缺条件明确不可用。 |
| `preview` | 卡面/插图/边框资源引用 | 预览引用可为空占位，但必须显式。 |
| `balance` | 定位、风险、测试场景、基线版本、遥测组 | 让编辑器和调参记录可追溯。 |

### 4.2 目标策略：不使用 `needTarget: bool`

```text
TargetPolicy
  SelectionMode: None | Optional | Required
  Scope: None | Self | SingleEnemy | SingleAlly | AnyAlly | AllEnemies | AllAllies
  MinimumTargets: int
  MaximumTargets: int
  AllowDeadTargets: bool
  RetargetOnInvalid: RejectPlay | ReopenSelection | SkipInvalidTargets
```

ACT1 可执行矩阵：`None`、`Self`、`SingleEnemy`。`SingleAlly`、`AnyAlly`、`AllEnemies`、`AllAllies` 是 Schema 预留，当前 Validator 必须拒绝它们进入生产奖励池，而不是让 UI 猜测或静默退化。`RequiresEnemyTarget` 是旧兼容字段，迁移后删除。

### 4.3 费用与效果列表

```text
CardCostDefinition
  CostType: Energy | Health | XEnergy | None
  Amount: int
  Timing: OnPlay
  FailurePolicy: RejectPlay
  CanCauseDefeat: bool        // Health 必填

CardEffectDefinition
  Order: int
  EffectType: DealDamage | GainBlock | LoseHealth | AddStatus | MoveSelfToZone
              | DrawCards | GainEnergy | ModifyCost
  TargetSelector: SelectedTarget | Self | AllEnemies | AllAllies
  Amount: int | FormulaDefinition
  CanCauseDefeat: bool       // 仅 LoseHealth 必填
  StatusKind: Strength | Vulnerable | EternalFlame (仅 AddStatus)
  DurationScope: Battle | Turn | PermanentEnemy
  DestinationZone: Exhaust (仅 MoveSelfToZone)
  Conditions: ConditionDefinition[]
```

ACT1 执行器只支持 `DealDamage`、`GainBlock`、`LoseHealth`、`AddStatus`、`MoveSelfToZone(Exhaust)`，其中可用状态为斗劲、易损、永炎。`Order` 是必填且连续的：例如烈拳为“伤害 -> 易损”，祝融残焰为“失去生命 -> 对所选敌人施加永炎 -> 自身移入消弭区”。费用是打出合法性的支付；自损可保留为有序效果以表达“先支付还是后结算”，并由 `LoseHealth.CanCauseDefeat` 声明致败语义；同一张卡不得重复表达同一笔生命成本。

### 4.4 示例：`wx_r_010` 的结构化含义

```yaml
id: wx_r_010
owner: { ownerKind: Character, characterId: wuzhu }
category: Skill
costs: [{ costType: Energy, amount: 2, timing: OnPlay }]
targetPolicy: { selectionMode: Required, scope: SingleEnemy, minimumTargets: 1, maximumTargets: 1, allowDeadTargets: false, retargetOnInvalid: RejectPlay }
effects:
  - { order: 1, effectType: LoseHealth, targetSelector: Self, amount: 3, canCauseDefeat: true }
  - { order: 2, effectType: AddStatus, targetSelector: SelectedTarget, statusKind: EternalFlame, amount: 4, durationScope: PermanentEnemy }
  - { order: 3, effectType: MoveSelfToZone, targetSelector: Self, destinationZone: Exhaust }
rarity: 地品
rewardPoolIds: [reward_cards]
upgrade: { canUpgrade: false }
tags: [wuzhu, self_harm, eternal_flame, act1]
```

该示例只说明结构，YAML 不是强制存储格式；推荐由 Godot Resource 序列化。说明文字可由这些字段生成并与本地化文案校验，不能反向解析。

### 4.5 Validator 必须阻断的错误

- 重复/空 ID、缺本地化键、角色归属矛盾、未知类别或池。
- 负费用、生命费用或 `LoseHealth` 未声明致败规则、未支持的 X 公式。
- 空效果、重复/跳号 `Order`、效果目标与 `TargetPolicy` 不兼容、无目标牌却引用 `SelectedTarget`。
- 未实现的友方/全体范围进入 ACT1 生产池；未知状态、持续域或移区。
- 断裂/循环升级、升级跨不兼容所有者、天品卡被错误标可升级。
- 预览资源未解析、不可用版本/条件缺少用户可读原因、平衡元数据为空。

## 5. 内部编辑器 MVP

### 5.1 推荐路线

使用 Godot `EditorPlugin + Resource + Definition Catalog + Validator + Preview`，不做玩家运行时编辑器。先完成数据迁移和校验，再做可视化编辑界面；否则会增加一套无法验证的内容源。

| 阶段 | 最小功能 | 不做内容 |
|---|---|---|
| E0 数据层 | 卡牌 Resource、Catalog、导入/保存校验、错误定位。 | 不做可视化编辑器。 |
| E1 编辑插件 | 卡表筛选、字段编辑、效果排序、目标策略预览、升级链接、只读校验面板。 | 不执行运行时战斗、不修改玩家存档。 |
| E2 内容审查 | 池成员检查、升级图、定义差异、卡面预览、固定种子测试入口。 | 不自动根据指标改数值。 |
| E3 后续 | 批量操作、遥测看板、遭遇模拟。 | 不属于 MVP。 |

### 5.2 编辑器交付验收

- 保存前显示字段级阻断错误和资源路径；无效卡不能加入 Catalog/奖励池。
- 卡面预览读取同一 `display`、`preview`、`costs`、`targetPolicy`、`effects`，不得另写 UI 假数据。
- 新增已有执行器支持的单敌卡，只需新增资源并挂入池，不修改 UI/Core/Controller。
- 同时加载两张名称、费用、目标、效果顺序都不同的卡，确认预览、结算和奖励不串用第一张定义。
- 资源编辑不接触 `RunState`、`BattleState`、奖励领取或节点离场。

## 6. 给开发部的实施清单

1. 以本 Schema 建立 Definition Resource、Catalog、枚举和纯 Validator；不要先做插件。
2. 为当前 21 张唯一 ID 建资源，并把初始牌重复数留在 StarterDeck 配置/RunState 的卡 ID 列表，不复制定义。
3. 为每个旧 `CardInfo` 建结构化迁移测试：ID、显示、费用、目标、效果顺序、消弭、升级、池成员均比对；失败即显式报错。
4. 将 `CardPoolCatalog`、角色初始套牌、奖励展示和战斗执行的读取入口逐步收敛到 Catalog；旧 `DataDefs` 只临时作为迁移 fixture。
5. UI 只读 `display`/`preview`/`targetPolicy`；Core/执行器只读 `costs`/`effects`；两者均不得按名称、ID、职业或固定数值分支。
6. 保持奖励状态边界：候选生成后冻结；关闭/跳过不消费候选或奖励入口；领取才写永久套牌；继续/返回地图只显示地图；合法下一节点点击才离开节点。
7. 在完成唯一数据入口和验证后再做 E1 插件，并在每次内容变更跑 Validator、双定义反证与硬编码扫描。

| 项目 | 风险/待决策 | 推荐处理 |
|---|---|---|
| 当前数值建议 | 未有足量 ACT1 实测，直接同时调整多张卡会失去归因。 | 本轮仅冻结建议和指标；下一轮一次只验证一个改动假设。 |

| 预留枚举 | 友方/全体/诅咒等未实现能力若误入生产池会形成假功能。 | Validator 以运行时支持矩阵阻断，不使用静默降级。 |
