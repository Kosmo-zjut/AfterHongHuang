# 02-卡牌数据结构

> 版本: 1.1.0 | 状态: B1 数据迁入契约冻结，待开发部实施 | 最后更新: 2026-07-20

> 策划契约来源：[03-玩法系统/12-卡牌数据与平衡设计.md](../03-玩法系统/12-卡牌数据与平衡设计.md)。本文件只定义开发迁移、编辑器边界与验收，不授权在本轮直接改动运行时代码。

## 1. 目标与边界

将当前 `DataDefs.cs` 中的 `CardInfo` 静态数组迁移为可校验的 `CardDefinition Schema v1`，使同一份集中定义驱动运行时效果、奖励池、升级、预览和后续编辑工具。

- 推荐承载：Godot `Resource` 定义资产（单卡 `CardDefinitionResource`，集中 `CardCatalogResource`）。这与 Godot Inspector、版本控制和引用校验兼容。
- 不做：面向玩家的运行时卡牌编辑器、运行时任意脚本执行、根据卡名或描述解析效果。
- 不在 UI、Core、场景控制器中写具体卡牌 ID、名称、职业名称、固定费用或数值分支。
- `CardDefinition` 是内容定义；奖励候选冻结、领取、跳过及节点离场继续由既有 `RewardPlan` / `NodeResult` 状态边界处理，不能混入卡牌资产。

## 2. 建议 C# 映射

以下名称是建议 API；实际命名可按编码规范调整，但字段语义不得缩减。

```csharp
public sealed class CardDefinitionResource : Resource
{
    public int SchemaVersion { get; init; }
    public string Id { get; init; }
    public CardDisplayDefinition Display { get; init; }
    public CardOwnerDefinition Owner { get; init; }
    public CardCategory Category { get; init; }
    public CardCostDefinition[] Costs { get; init; }
    public TargetPolicy TargetPolicy { get; init; }
    public CardEffectDefinition[] Effects { get; init; }
    public CardRarity Rarity { get; init; }
    public string[] RewardPoolIds { get; init; }
    public CardUpgradeDefinition Upgrade { get; init; }
    public string[] Tags { get; init; }
    public CardAvailabilityDefinition Availability { get; init; }
    public CardPreviewReference Preview { get; init; }
    public CardBalanceMetadata Balance { get; init; }
}
```

运行时执行器只接收 `CardDefinitionResource` 的已校验投影和明确的 `CardEffectDefinition[]`。描述文本由本地化字段生成或校验，不是效果输入。当前 `CardInfo.Value`、`SelfDamage`、`HasSecondary`、`SecondaryType`、`SelfGuardValue`、`Exhausts` 是迁移源，不是 Schema v1 的长期模型。

## 3. 分阶段实施

| 阶段 | 交付 | 完成条件 |
|---|---|---|
| P0 数据冻结 | 导出当前卡表快照、建立 `CardDefinitionResource` / `CardCatalogResource`、实现纯数据校验器。 | 所有当前 ID、效果顺序、目标、奖励池和升级关系可无损表达。 |
| P1 双读迁移 | 编写 Definition -> 运行时投影适配层；以同一输入比较旧 `CardInfo` 与新定义。 | 未变卡保持 ID、费用、目标、效果、消弭和升级映射一致；B1 的 7 个已批准字段差异必须精确匹配玩法文档，失败明确报错。 |
| P2 切换入口 | `CardPoolCatalog`、奖励、升级、战斗预览只读 `CardCatalogResource`。旧数组仅保留迁移 fixture/测试，随后删除重复生产定义。 | 新增一张同类卡不修改 UI/Core/Controller 分支。 |
| P3 编辑器 MVP | Godot `EditorPlugin`：目录、筛选、编辑、效果排序、目标预览、升级链接与校验面板。 | 保存前可看到阻断错误；预览来自同一 Resource。 |
| P4 延后能力 | 资源模拟、池概率检查、批量差异、遥测查看。 | 不属于当前 MVP 阻断项。 |

编辑器只在 P0-P2 已有唯一数据入口后开始。先做界面会把 `DataDefs` 与 Resource 变成两套事实来源，风险高。

2. 将 [12-卡牌数据与平衡设计.md §3.1](../03-玩法系统/12-卡牌数据与平衡设计.md) 作为 `balanceVersion=B1-20260720` 的唯一目标值。仅 `wx_02_p`、`wx_r_005`、`wx_r_006`、`wx_r_007`、`wx_r_008`、`wx_r_009`、`wx_a1_boss_002` 可与旧快照不同；其余字段和卡牌必须保持一致。
3. 对每张卡拆成费用列表、目标策略和有顺序的效果列表；不要把“自损 + 伤害 + 易损”重新压回一个主值与一个副值。
4. 把 Boss 卡的当前消弭事实写入迁移测试：三张 Boss 卡当前均为不消弭；`祝融残焰` 为消弭。B1 也不改变任何 Boss 卡的消弭状态。
5. 给 `CardCatalogResource` 建立显式池定义和升级关系；禁止 `GetCardById` 遍历多个数组或以“第一个存在的卡”为兜底。
6. 以双读比较替换 `DataDefs` 的生产入口，比较失败时拒绝启动相关内容并输出 ID 与字段路径。
7. 完成 P1 后再接编辑器插件；编辑器不可直接写运行时临时状态、奖励计划或玩家永久套牌。

## 5. 工具必须校验的字段

| 校验类别 | 阻断规则 |
|---|---|
| 标识与本地化 | ID 非空、全目录唯一、满足命名规则；名称/描述/效果摘要的本地化键存在；开发期 fallback 文本非空。 |
| 所属与类别 | `Neutral` 不得同时填写角色 ID；`Character` 必填角色 ID；类别必须是受支持枚举。 |
| 费用 | `Costs` 至少有一个明确费用语义；数量不得为负；`X` 费用须有上限和结算公式；生命费用或 `LoseHealth` 效果必须声明能否致败。 |
| 目标 | `TargetPolicy` 必填；无目标卡不得携带 `SelectedTarget` 效果；单体敌方效果不得使用 `Self` 策略；MVP 不支持的 Ally/All 范围必须报“不受运行时支持”。 |
| 效果 | 效果列表非空、`Order` 唯一且连续；效果类型、数值公式、目标选择器、持续域合法；`Exhaust` 必须是显式移区效果。 |
| 池与升级 | 稀有度、池 ID 均存在；升级目标存在、无环、同一拥有者和可支持类别；不可升级卡显式标记。 |
| 资源与版本 | 预览资源引用可解析或允许明确空占位；版本、特性条件和禁用原因可读。 |
| 平衡元数据 | 定位、风险标签、测试场景、变更理由和遥测分组不能为空；数值修改需记录基线版本。 |

## 6. 开发验收清单

- [ ] 执行器按 `Effects` 和 `TargetPolicy` 结算，不读取名称、描述或固定 ID 决定行为。
- [ ] UI 依据 `TargetPolicy` 提示/选择目标；`None`、`Self`、`SingleEnemy` 均可用，未支持范围明确禁用并报告。
- [ ] 新卡从目录加入一个已存在奖励池后，可在奖励、预览和战斗入口出现，且不修改 UI/Core/Controller。
- [ ] 以两张不同名称、数值、目标和效果顺序的测试卡走同一入口，结果不沿用第一张定义。
- [ ] 21 张定义的双读结果满足 B1：除 7 张批准改动卡的指定字段外均一致；不一致时输出字段级差异，禁止静默回退。
- [ ] B1 的两张消弭卡 `wx_r_006`、`wx_r_008` 只能由定义中的 `MoveSelfToZone(Exhaust)` 表达；不得用卡名/ID 分支将其移出牌堆。
- [ ] 无效定义不能进入 Catalog：重复 ID、断升级、目标不匹配、空效果、缺本地化键、未知池、未解析资源均可复现报错。
- [ ] 执行硬编码扫描：`scripts/UI/`、`scripts/Core/`、`scripts/Map/` 中不存在用具体卡名、ID、职业名、费用或数值决定生产行为的分支；测试 fixture / 数据定义命中须逐项说明。
- [ ] 奖励候选生成/领取/跳过/关闭仍使用既有计划状态；更换 CardDefinition 不得提前消费奖励、提交节点或离开节点页。

## 7. 已知风险

- Godot `Resource` 在多人并线下可能产生 `.tres` 合并冲突。P0 应采用“一卡一资源 + 目录索引”或稳定文本序列化，并限制单人维护同一 Catalog 索引。
- 当前 MVP 仅支持敌方/自身目标与少量效果。Schema 可以声明更大枚举，但 Validator 必须阻止未实现的范围进入生产池。
- `斗劲`、护体、易损、永炎等战斗状态属于 `BattleState`。CardDefinition 只声明施加何种状态及其目标/持续域，不能把临时层数写进 `RunState` 或卡牌资产。
